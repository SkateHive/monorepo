SkateHive is a skateboarding social network built on the Hive blockchain. Anyone can join by email, wallet, Farcaster, or a Hive key — and post, vote, and comment immediately, whether or not they own a single crypto key. Behind that simplicity sit two Next.js backends, two client apps, and three distinct databases. This page maps all of it.

02 — The core idea

Lite accounts & the
@skateuser trick

Hive requires a cryptographic key to do anything. Most new skaters don't have one — so SkateHive lets them act through a shared Hive account, @skateuser, while the UI overlays the real author's identity. The link between "who really did this" and "what hit the chain" is the soft post / soft vote registry in the userbase DB.

Lite account

no key

Signed up with email / wallet / Farcaster and hasn't linked a Hive key.

  • Server signs with the shared @skateuser key
  • A userbase_soft_posts / _soft_votes row records the real author
  • The feed overlays their name, avatar & profile on the post and on replies
  • Works forever — upgrading is optional

Full account

own key

Linked Hive via Keychain, got sponsored, or stored a posting key.

  • Posts under their own @username on-chain
  • Key signed by Keychain, or by an AES-256-GCM key held in userbase_hive_keys
  • Full blockchain ownership — no shared account
  • Reached via sponsorship, link, or manual key storage

↳ What happens when a lite user votes

01
Tap vote
Client sees kind: "userbase" and POSTs to /api/userbase/hive/vote with its Bearer token.
02
Resolve user
api hashes the token, finds the userbase_sessions row, resolves the real user.
03
Sign & broadcast
Server signs the vote with the shared key and broadcasts to Hive immediately.
04
Record attribution
A userbase_soft_votes row links the real user to (author, permlink).
05
Overlay in feed
The feed joins soft rows back in and shows the real skater (posts and replies), not @skateuser.
Not a queue. Broadcasts are synchronous — a soft row is attribution, not a job. No background workers, runs on Vercel's free tier. The four entry points (email · EVM · Farcaster · Hive Keychain) are all equal citizens; the entry point never limits what you can do.

04 — Traffic

Who calls what

The same logical user shows up with two different session transports depending on the client. That split is the source of most of the architecture's friction.

Mobile

spans both backends

  • api.skatehive.app — feed, videos, balance, profile, leaderboard, spotmap, transcode, and all userbase auth + server-custody hive actions
  • skatehive.app — no API calls anymore; only the caption permalink text points there
  • Classic key accounts encrypt the WIF on-device (PBKDF2 + AES-256, PIN/biometric); lite accounts hold only an opaque Bearer token
Web

proxies the write-core

  • hive/vote, comment & follow now proxy to api — the web routes forward the session (cookie value sent as Bearer); api is the single owner of the broadcast + soft rows
  • The client fetches read data (feed, leaderboard, highest-paid) from api.skatehive.app
  • Still owns the browser-only flows: identities (EVM/Farcaster), encrypted keys, sponsorships, merge, magic-link, bootstrap
Bearer token
Mobile transport. Authorization: Bearer <token> → hashed → userbase_sessions row.
Refresh cookie
Web transport. userbase_refresh httpOnly cookie → the same userbase_sessions rows. The two transports are interchangeable at the DB level.
Hive writes (web)
vote / comment / follow on web now forward to api.skatehive.app (cookie value sent as Authorization: Bearer — api hive routes are Bearer-only). One implementation; the web no longer signs/broadcasts these itself.
Instagram
Unified on api.skatehive.app (dual-auth: posting-key signature or userbase session). Web user cross-posts proxy to api; moderator force-post still runs on web. Both write userbase_instagram_posts.
Heavy jobs
Leaderboard recompute, video transcode, IG scraping all run off-Vercel on the Mac Mini / Oracle / Pi over Tailscale.

05 — Honest assessment

Is the split smart?

Separating the read/data API from the web app is reasonable, and keeping heavy work off Vercel is the single biggest win. The strain comes from userbase being implemented twice over the same tables — once per backend, with two different auth transports.

Split-brain userbase (now being resolved — see #1). Session creation, hive broadcast, and soft-post writes existed as parallel code in both repos. The duplicated write-core (vote/comment/follow) has been consolidated onto api via proxies; account-update/report + bootstrap still live in both.
